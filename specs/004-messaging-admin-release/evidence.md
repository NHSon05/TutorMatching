## Source and contract review findings

1. **No new feature routes yet.** Existing controllers include AdminController, AdminTutorReviewsController and CatalogController; messaging, notifications, article, dashboard and audit routes are planned. A validated design document cannot establish runtime parity. Every story must compare generated runtime OpenAPI and behavior against the design before closure.
2. **CSRF compatibility discrepancy.** `backend/src/TutorMatching.Api/Security/ApiSecurityExtensions.cs` returns 400 for invalid CSRF; `contracts/api.md` common behavior says 403. Existing hiring tests assert 400. Preserve current behavior in setup; explicitly reconcile prose/runtime expectations before story closure rather than changing authentication middleware here.
3. **Canonical state discrepancy.** `HireRequest.StatusCode` and existing hiring tests use `PENDING`; T039 names `PENDING_TUTOR_RESPONSE`. `TutorProfileStatus` includes `DRAFT`, omitted by T039. AccountStatus also includes `INACTIVE` (read state), while lock/unlock mutations allow ACTIVE/LOCKED only. New dashboard DTOs must not invent a status rename or silently omit a zero group. Correct the future task wording before implementation.
4. **Cookie documentation discrepancy.** `JwtCookieTokens.AccessCookie` is `accessToken`; `ApiSecurityExtensions` reads that cookie. The project map's session-cookie name is not the runtime access-cookie name. Keep OpenAPI security tied to source; no session implementation change in Phase 1.
5. **Missing executable test tasks.** T010/T011/T017/T018 are mentioned in dependency/parallel notes but absent from task checkboxes. There are 46 defined task IDs, not 50. This blocks evidence-first US1/US2 implementation until backend/frontend authorization, replay, notification and SignalR tests are explicitly restored. Phase 1 fixture tests do not replace them.
6. **Schema work remains Phase 2.** Baseline Message has no ClientMessageId; Article already has AuthorUserId, title/slug limits and unique slug but no Version. Notification has message references/read state but no new outbox/dedup guarantees. Setup fixtures deliberately use the current migrated schema and do not introduce future columns/migrations.
7. **Existing contracts remain authoritative.** Admin users pagination and `/users` alias, catalog vocabulary and payloads must remain compatible; no generic replacement controller is added. Notification type codes must reflect current producers plus an explicitly documented planned message code.
8. **SignalR and release dependencies are unverified.** Authenticated hub isolation, session revocation, commit ordering, reconnect multi-page recovery and load remain required. Sprint 3 `specs/003-hire-negotiation/tasks.md` T046–T050 remain unchecked and block release, not isolated setup.
9. **Existing dependency warnings.** Backend baseline passes but reports NU1902/NU1903 for `System.Security.Cryptography.Pkcs` 10.0.0: GHSA-2fmv-rv2c-59x7 (moderate) and GHSA-846f-f764-76mx (high). These predate Phase 1; dependency remediation is not included in setup and must be triaged before release.
10. **Fixture verification correction.** First behavioral run passed both messaging checks but failed the admin audit assertion (expected 3, actual 7): real authentication during seeding adds audit rows. The assertion now scopes to Article events rather than incorrectly assuming the entire audit store contains only seeded content history. No runtime audit behavior was changed.

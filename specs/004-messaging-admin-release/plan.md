# Implementation Plan: Messaging, Administration and MVP Release

**Branch**: `main` (no new branch created) | **Date**: 2026-11-01 | **Spec**: [spec.md](spec.md)

## Summary

Complete request-scoped text messaging, user-owned notifications, safe administration and
release evidence. Extend existing entities, auth/session controls, catalog and review workflows;
replace mock screens. Work in independently verified phases, starting with messaging.
This is a design plan, not a claim of implementation or release readiness.

- Constraints: backend authorization, CSRF, no private payload logging, immutable hiring terms,
  no admin message browsing, no broker or Socket.IO dependency.
- Scale: two participants per request; text messages only; operational dashboard counts.

## Delivery sequence and independent checkpoints

1. **Setup / baseline**: build FR/SC evidence matrix, inspect current contracts/schema, rerun narrow
   baselines, record existing failures, generate OpenAPI3.1 schemas from contracts/api.md, analyze
   spec/plan/tasks. No app implementation until required interface/authorization cases are explicit.
2. **Foundation**: synthetic two-party/unrelated/locked/admin fixtures; additive indexes/version
   and replay/outbox migration; migration/backfill checks; atomic audit and shared error patterns.
3. **US1 Messaging (P1, first MVP)**: participant conversation list/history/send/read, stable
   cursors, send replay identity, notification intent; replace mock `/messages` with real UI.
   Checkpoint: both actors send/read/page; uncertain retry stores one message; outsider denied;
   notifier failure/restart retains message and eventually produces one notification.
4. **US2 Notifications (P1)**: list/count/read-one/read-all/open-reference, safe routing,
   SignalR updates, reconnect reconciliation and account-change cache cleanup. Verify every existing review/hiring type
   plus message type, absent references, concurrent arrival/read-all and worker replay.
5. **US3 Account administration (P1)**: extend user list/search/detail; confirmed lock/unlock,
   expectedVersion, self-lock denial, session revocation and atomic audit. Verify current sessions,
   public discovery removal, concurrent admins, preserved history and denied non-admin calls.
6. **US4 Content/catalog/monitoring (P2)**: versioned article lifecycle + public published-only
   read; extend current catalog with stale-write protection; read-only request summaries/detail
   excluding private conversation content and unrelated learner contact. Independently test all.
7. **US5 Dashboard/audit (P2)**: source-backed consistent counts and filtered safe audit list;
   replace mocks, show genuine zeros; verify source totals and redaction.
8. **US6 Release (P1, integration gate)**: finish Sprint3 remaining gates, full AC-01–10 evidence,
   Chromium/Firefox/WebKit desktop/mobile+keyboard,100-user load, safe sample-data setup,
   deployment/configuration guide and isolated backup/restore rehearsal. Run converge; no release
   claim with unresolved critical failures. Production deployment is a separate authorized action.

## Cross-cutting implementation rules

- Each state mutation uses current actor, explicit concurrency/replay policy and one database
  transaction for its business changes and audit. Retain snapshots and existing lock order.
- Message transaction writes message + durable notification intent. Worker writes notification
  and completes intent atomically with unique event-recipient identity. Existing hiring/review
  notification transactions remain unchanged (ADR-011).
- Read receipts acknowledge only loaded recipient message IDs; never mark unseen arrivals or
  sender-owned messages. Read-all notification action binds a server-issued list snapshot.
- Hooks own SignalR connection/subscription/cache/mutations; reducer owns message draft/replay state. Account switch
  stops the old connection, removes handlers, cancels private work, clears caches and resets draft; no private data in localStorage.
- On uncertain send retry retain operation ID + exact payload; changed draft gets new ID.
  On409 keep draft and fetch current state; never automatically repeat an admin decision.
- REST handles sends/receipts/history; SignalR publishes committed-change hints. Events are not
  durable delivery acknowledgements. Reconnect/focus/manual refresh reconciles via authorized REST.
- No online presence indicator, attachments or message edit/delete in this MVP.

## Complexity Tracking

No governance violations. One database outbox is justified by FR-006: direct notification-write
failure must not discard a committed message. An in-memory retry cannot survive process restart.
